# SquareDotSerial Godot 工程通用要求

## 1. 文档目的

本文件用于统一整理当前项目的通用工程约束，作为后续开发、重构、审查、模块抽象与交付汇报时的默认执行标准。

本文件聚焦：

- 工程结构约束
- 场景与脚本边界
- UI 模块化要求
- 代码风格要求
- 本地化要求
- 文件交互与桌面行为要求
- 审查与交付要求

本文件不替代功能计划文档，但对实现方式具有约束力。

## 3. 总体原则

### 3.1 功能优先，但架构必须为后续体验留口

- 不要求先做“纯美化”，但从第一阶段开始就必须为视觉层、反馈层、复用组件和后续迭代预留结构。
- 不能为了快速实现功能，把 UI、逻辑、状态、反馈全部写死在单个页面脚本里。
- 项目优先追求：
  - 可读性
  - 可维护性
  - 可扩展性
  - 可复用性
  - 编辑器可见性

### 3.2 优先做可持续结构，而不是一次性页面

- 第一版就要建立可复用预制组件，而不是先把页面硬拼出来，后面再返工。
- 高频 UI 组合必须尽早抽象。

### 3.3 遇到不确定项时先停下确认

- 若无法判断当前实现是否符合既有结构，应先审查现状再改。
- 若存在多种实现路径且会影响后续结构，应先列出方案与取舍。

## 4. 场景与脚本边界

### 4.1 优先使用场景，不优先用代码拼 UI

- 所有能在 Godot 编辑器中直接搭建的内容，必须优先放进 `.tscn`：
  - UI 布局
  - 节点层级
  - 默认资源绑定
  - 常见控件组合
  - 面板骨架
  - 可复用组件
- 脚本应主要负责：
  - 行为逻辑
  - 状态同步
  - 数据绑定
  - 动态内容填充
  - 运行时确实无法静态表达的结构

### 4.2 只有以下情况才允许动态创建节点

- 运行时数量不确定
- 运行时结构不确定
- 编辑器静态场景表达成本明显更高
- 确实属于数据驱动内容，而非固定 UI 骨架

### 4.3 目标要求

- 打开编辑器时，主要页面和面板应能直接看见真实节点结构，而不是空根节点。
- 固定 UI 不应隐藏在 `_build_ui()`、`add_child()` 大段构造逻辑里。

### 4.3.1 页面级功能区必须是布局容器

- 像 `ProjectSection`、`MediaSourceSection`、`OutputListSection` 这类页面级功能区，根节点默认应使用 `Container` 类型。
- 推荐优先使用：`PanelContainer`、`VBoxContainer`、`HBoxContainer`、`MarginContainer`。
- 这类节点被放入 `ScrollContainer` 或其他布局容器时，必须能够用自身子节点的真实最小尺寸参与父级布局计算。
- 不应让父级滚动、收缩、换行依赖手工填写的 `custom_minimum_size` 去“猜”内容高度。
- 审查时必须确认：
  - 父级滚动条是否由真实内容高度触发
  - 根节点是否真的承担布局语义，而不是仅仅作为脚本挂载点

### 4.3.2 页面级场景中必须直接放真实条目

- `ProjectSection` 这一级别的场景属于“业务功能区场景”，不是“包装壳场景”。
- 这类场景中应直接存在：
  - 标题
  - 分隔线
  - 列表
  - 行编辑模块
  - 文件面板
  - 工具按钮
- 不允许页面级场景退化成“根节点下只有一个 `Card` / `PanelCard` 子节点”，再由脚本或 `@tool` 在运行时注入实际条目。
- 这会带来以下问题：
  - 编辑器中看不到真实节点结构
  - 无法直观调试布局和滚动行为
  - 平白增加一层无业务意义的节点
  - 破坏“场景优先、编辑器可见”的目标

### 4.3.3 模块粒度应优先小而稳定

- 优先抽象的小模块是：
  - `Label + OptionButton`
  - `Label + LineEdit`
  - `Label + SpinBox`
  - `文件路径 + 浏览/保存/加载`
  - `按钮工具条`
- 页面级功能区应作为这些小模块的组合容器存在，并在 `.tscn` 中直接排布出来。
- 不推荐优先抽象“包含大量不可预测内容的大卡片模块”，再把页面级内容塞进里面。
- 推荐结构：
  - 小模块：负责单一输入或显示组合
  - 页面级场景：负责在场景里把这些小模块组装成完整功能区
- 不推荐结构：
  - `SectionScene -> CardScene -> 脚本注入一批真实条目`

### 4.4 节点引用与通信规范

本项目默认采用“组件内部自治，跨组件信号通信，父节点中介组装”的引用策略。目标不是机械替换某一种写法，而是降低节点树调整、节点重命名、面板拆分时的破坏范围。

#### 4.4.1 基本原则

- 每个场景/预制体只应直接维护自己职责范围内的节点引用。
- 父节点负责组装子组件、注入依赖、转发状态，不负责深入操作子组件内部叶子控件。
- 子组件对外应暴露稳定 API 与 `signal`，而不是要求外部了解其内部节点树。
- 判断引用方式是否合理的标准，不是“能不能运行”，而是“改节点树后会不会波及多个脚本”。

#### 4.4.2 选择顺序

默认按以下顺序选择引用与通信方式：

1. 组件内部固定子节点：优先场景内自维护引用。
2. 父子组件协作：优先由父节点持有子组件根引用。
3. 同级组件协作：优先 `signal`，由父节点中介。
4. 跨场景批量协作：优先 `group`。
5. 全局服务与全局状态入口：优先 `autoload`。

#### 4.4.3 `%唯一名称` 的使用范围

- `%NodeName` 只应用于组件或场景内部，且这些节点确实属于该脚本直接管理的实现细节。
- 小型、自封闭、复用型 prefab 内部允许继续使用 `%`，不要求强制改成 `@export`。
- 若一个脚本通过 `%` 持有大量叶子控件，且这些控件分属多个功能区，应优先考虑拆分子场景，而不是继续扩充 `%` 引用列表。
- 不应通过 `%` 穿透访问其他组件的内部节点。
- 不应把 `%` 当作跨模块通信方案；它只能解决当前场景内节点路径易变问题，不能解决架构耦合问题。

#### 4.4.4 `@export` 的推荐用途

- `@export` 主要用于依赖注入，而不是无差别替代所有 `%`。
- 适合使用 `@export` 的情况：
  - 父节点需要显式绑定某个子组件根节点。
  - 某个依赖应在 Inspector 中可见、可校验、可替换。
  - 节点层级可能调整，但依赖关系本身稳定。
  - 组件需要暴露少量可配置接线点。
- 不适合使用 `@export` 的情况：
  - 只是组件内部几个固定子控件。
  - 同一类简单引用过多，导致 Inspector 变成一排人工接线槽。
  - 本质问题是组件职责过大，而不是引用方式不对。
- 父节点应优先 `@export` 子组件根类型，而不是大批量 `LineEdit`、`Button`、`SpinBox` 这类叶子控件。

#### 4.4.5 信号通信规范

- 同级节点之间不直接互相查找并调用内部方法，默认由父节点负责连接 `signal` 并协调行为。
- 子节点向上报告事件、请求操作、同步状态时，应优先使用 `signal`。
- 父节点接收 `signal` 后，可决定直接处理、转发给服务层或更新其他子组件。
- 子组件对外 `signal` 应表达业务语义，而不是暴露实现细节。
- 推荐：`send_requested(payload)`、`recipe_changed(recipe)`、`connect_requested(config)`
- 不推荐：把 `button_clicked()`、`line_edit_changed(text)` 直接当作跨模块业务接口

#### 4.4.6 Group 与 Autoload 的边界

- `group` 只用于横切能力、批量通知、跨场景统一收集对象，不用于替代本地 UI 接线。
- `autoload` 只用于全局服务、全局配置、全局资源入口，不用于承接本该由父节点协调的局部页面逻辑。
- 若某个 UI 面板必须依赖全局对象，应明确其职责是消费服务，而不是把页面逻辑散落到全局单例调用中。
- 若 `ui_modules/0_Core_Autoload` 下存在多个核心 helper，默认应通过单一全局入口脚本统一对外暴露，例如 `UICore`；其他模块优先依赖该入口，而不是分别 `preload` 多个核心 helper 脚本。

#### 4.4.7 禁止做法

- 链式 `get_parent().get_parent()` 查找外部节点。
- 子组件脚本直接依赖固定兄弟节点名称。
- 父节点直接修改子组件内部叶子控件值，而不经过子组件 API。
- 通过节点路径约定在多个场景间隐式耦合。
- 为了少写 `signal`，把同级通信写成互相持有引用。

#### 4.4.8 推荐重构方向

- 当一个面板根脚本持有大量输入框、按钮、列表、标签时，应优先按功能区拆成多个子场景。
- 每个子场景内部自行维护自己的子节点引用。
- 面板根脚本只依赖这些子场景的根组件，并负责组装、状态同步和信号转发。
- 重构的首要目标是缩小单脚本的“已知节点树范围”，而不是统一某一种语法。

#### 4.4.9 落地检查标准

- 重命名某个输入框或调整局部节点树时，是否只影响该组件自身。
- 替换某个子组件实现时，父节点是否仍可通过同一组 API / `signal` 工作。
- 新增一个并列功能区时，是否无需让旧组件知道它的存在。
- Inspector 中暴露的 `@export` 引用，是否是真正的依赖，而不是原本应封装在组件内部的细节。

#### 4.4.10 RootControl UI 聚合层

对于主场景这类“仿真世界 + 大量 UI 工作台”的页面，必须把 UI 作为 `RootControl` 的内部职责管理，避免 `main.gd` 直接持有几十个 UI 叶子节点。本规则是强制要求，不是后续优化建议。

执行要求：

- `main.gd` 只应直接引用仿真世界对象、Recorder、Camera、Renderer 以及 `RootControl` 根节点。
- `main.gd` 引用非 UI 节点时，应优先使用明确的直接路径、`@export_node_path` 或注入引用；不应为了方便把 `DataRecorder`、`Camera3D`、`ROV` 等节点也批量设成 `%唯一名称`。
- `RootControl` 负责持有其内部 UI 节点引用，并对外暴露稳定接口，例如：
  - `apply_static_texts()`
  - `configure_controls()`
  - `set_status(text, color)`
  - `set_resource_paths(payload)`
  - `set_dashboard(payload)`
  - `set_chart_series(payload)`
  - `get_runtime_inputs()`
  - `get_assembly_inputs()`
- `_apply_static_texts()`、控件默认范围配置、路径显示、按钮文本刷新、图表标题刷新、资源面板行文本刷新等纯 UI 方法，必须移动到 `RootControl` 或更小的页面级 UI 脚本中；`main.gd` 中不允许继续保留这类纯 UI 方法。
- `main.gd` 不应知道 `RootControl` 内部的 `Label`、`Button`、`SpinBox`、`RichTextLabel` 叶子节点路径；它只通过 `RootControl` 的接口和信号交互。
- `RootControl` 可以通过 `@export` / `@export_node_path` 引用其内部关键子组件根节点。因为这些节点属于 `RootControl` 内部，使用导出引用或 RootControl 内部相对路径，比把大量节点设成 `unique_name_in_owner` 更利于编辑器调试。
- `%唯一名称` 只保留给少量跨脚本确实需要的场景根或小型组件内部节点；不应为了让 `main.gd` 访问 UI 叶子节点而批量设置唯一名称。完成 RootControl 聚合后，UI 叶子节点即使仍暂时带有 `unique_name_in_owner`，也不允许被 `main.gd` 直接访问。
- RootControl 对外 signal 应表达业务动作，而不是控件细节，例如 `start_sim_requested`、`record_toggle_requested`、`machine_save_requested`、`thruster_transform_changed(index, position, rotation)`。
- RootControl 内部若继续变大，应继续拆为页面级脚本：`AssemblyPanel`、`ChartWorkspace`、`ResourcePanel`、`PlaybackPanel`、`DashboardPanel`。RootControl 只负责组装这些页面级组件。

重构顺序建议：

1. 先把静态文本、本地化刷新和控件默认范围配置从 `main.gd` 移到 `RootControl`。
2. 再把按钮连接迁移为 RootControl 业务信号，由 `main.gd` 连接这些信号。
3. 继续迁移 Dashboard、图表、资源路径、装配编辑器等 UI 更新方法。
4. 最后按功能拆分页面级 UI 脚本，让 RootControl 只做组装与转发。

验收标准：

- 新增 UI 控件时，默认只修改 `RootControl` 或所属页面级 UI 脚本，不需要在 `main.gd` 增加叶子节点引用。
- `main.gd` 中不应出现 `@onready var xxx = %SomeUiNode`、`get_node("...Button")` 这类 UI 叶子节点引用。
- `main.gd` 中不应出现 `_apply_static_texts()` 或同等职责的纯 UI 文本刷新方法。
- 主场景中 `unique_name_in_owner = true` 的 UI 节点数量应随重构逐步下降，只保留有明确跨组件用途的根节点。
- `main.gd` 的职责收敛为仿真调度、业务服务调用、数据组合和 RootControl 信号处理。

## 5. UI 结构与复用要求

### 5.1 UI 从一开始就要按组件体系搭建

- UI 不是只看功能是否可点通，还要考虑后续统一风格、反馈、替换和扩展。
- 页面层只负责组装，不负责重复造轮子。

### 5.2 高频组合必须预制化

下列组合默认视为高频组合，应优先做成预制场景：

- `Label + LineEdit`
- `Label + SpinBox`
- `Label + OptionButton`
- `Label + 只读数值显示`
- `按钮工具条`
- `状态徽标`
- `文件路径编辑 + 浏览 + 保存/加载`
- `协议字段编辑卡片`
- `带标题的卡片/分组容器`

### 5.3 视觉与反馈层必须预留统一入口

- 组件可以包含：
  - Tween 动画
  - Hover / Press / Focus 反馈
  - 点击音效
  - 状态切换反馈
- 但这些反馈不能散落在业务脚本里，必须有统一接入层或基类。

### 5.4 UI 设计原则

- 专业工具感优先，不做游戏化界面。
- 信息密度可以高，但分区必须清楚。
- 颜色首先服务于状态语义，而不是装饰。
- 动效应短、轻、明确，只用于反馈。

## 6. 模块化要求

### 6.1 可复用元素必须抽模块

在开发和审查中，只要发现以下对象具有复用价值，就应评估模块化：

- 多页面重复出现的 UI
- 同一页面内部重复出现的组合控件
- 明显可独立测试、独立说明、独立复用的功能块

### 6.2 模块设计原则

每个模块必须满足：

- 高内聚：只解决一类问题
- 低耦合：尽量不依赖外部节点路径与页面结构
- 可复用：可以被其他场景拖入使用
- 可替换：外部通过信号、导出参数或明确 API 交互
- 内部自治：模块内部自行维护子节点引用，不要求外部感知其叶子节点结构
- 边界清晰：模块对外只暴露必要的根组件引用、导出配置、`signal` 与公开方法

补充要求：

- 模块抽象应优先面向“稳定复用的局部组合控件”，不要优先面向“只是视觉外壳的大包装层”。
- 若一个模块的主要作用只是包住整块页面，导致其内部真实条目不在该场景中可见，则默认视为不合理抽象。
- 页面级 `Section` 更接近业务组合场景，不应默认塞进 `ui_modules/` 这一层当成通用控件。

### 6.3 模块目录要求

一个模块对应一个独立文件夹。默认结构：

```text
ui_modules/模块名/
  模块名.tscn
  模块名.gd
  README.md
```

按需要可扩展：

```text
ui_modules/模块名/
  模块名.tscn
  模块名.gd
  README.md
  assets/
  icons/
  styles/
  examples/
```

### 6.4 模块脚本要求

- 使用显式类型
- 提供稳定 API
- 通过 `signal` 与外部通信
- 优先通过 `@export` 暴露配置
- 优先通过 `@export` 暴露“依赖的组件根引用”，而不是大批量暴露叶子控件
- 模块内部允许使用 `%` 管理固定子节点，但应限制在模块私有实现范围内
- 避免把业务逻辑塞进通用模块
- 避免依赖页面特定父节点结构

不推荐做法：

- 链式 `get_parent().get_parent()`
- 假定固定场景层级
- 组件脚本直接操作外部业务对象内部状态

### 6.5 模块文档要求

每个模块都必须带 README，且应简明但完整，至少包含：

- 模块用途
- 适用场景
- 目录结构
- 对外属性
- 对外信号
- 使用步骤
- 最小示例
- 注意事项

README 示例内容建议：

```gdscript
var panel: FileDialogPanel = preload("res://ui_modules/FileDialogPanel/FileDialogPanel.tscn").instantiate()
panel.save_requested.connect(_on_save_requested)
panel.load_requested.connect(_on_load_requested)
panel.set_full_path("user://square_dot_serial/recipes/demo.json")
```

## 7. 代码风格与类型要求

### 7.1 强制静态类型

- 脚本中的变量、参数、返回值、关键临时值，凡是合理可标注类型的，都应显式标注。
- 避免依赖隐式推断。

### 7.2 禁止使用 `:=`

- 本项目默认拒绝 `:=` 风格。
- 应使用显式类型写法，例如：

```gdscript
var path: String = ""
var steps: Array[Dictionary] = []
var file_dialog: FileDialog = %FileDialog
```

而不是：

```gdscript
var path := ""
var steps := []
```

### 7.3 脚本职责要求

- 页面脚本负责页面调度与组合
- 面板脚本负责局部业务交互
- 组件脚本负责组件自身行为
- 核心逻辑放入业务模块，不写进 UI 组件

### 7.4 可读性要求

- 命名清晰
- 函数职责单一
- 避免超长函数堆积多个职责
- 避免把节点创建、文本本地化、信号连接、业务逻辑混在一起

### 7.5 脚本文档注释要求

- 所有可复用模块脚本、核心脚本以及后续新增脚本，默认都要补齐 Godot `##` 文档注释，不允许只给局部代码随意加零散说明。
- 每个脚本开头必须有一段整体说明，至少覆盖：
  - 脚本职责与主要功能
  - 依赖的关键节点、服务或前置条件
  - 外部如何实例化、挂载或调用
  - 适合放在哪一层使用，例如通用模块、页面层、autoload 或业务脚本
- 每个方法前都必须有简明注释，至少说明：
  - 该方法负责什么
  - 每个输入参数分别代表什么
  - 有返回值时返回什么、调用方可依赖什么结果
- 所有可被外部访问的方法都必须额外提供一个简短调用示例。示例格式要求：
  - 先描述一个实际调用场景
  - 再给出与当前 API 一致的正确调用代码
  - 示例必须短小，只覆盖当前方法的典型调用，不写成整段业务流程
- 私有辅助方法不强制提供调用示例，但仍必须说明参数语义，避免后续维护时误用。
- 注释内容必须和真实实现一致；禁止保留过期参数名、旧行为描述、已经失效的示例代码。
- 修改代码、重构节点结构、调整方法签名或变更模块职责时，必须同步核对并更新相关注释；“代码改了、注释以后再补”在本项目中视为未完成。
- 审查时若发现注释与实现不一致，应视为需要立即修正的问题，而不是可忽略的文档瑕疵。

## 8. 本地化要求

### 8.1 必须支持本地化

- 项目从中文开始做本地化，但架构必须从一开始支持多语言扩展。

### 8.2 使用 Godot 推荐方案

- 采用表格式翻译源维护多语言文本。
- 推荐使用 CSV 作为翻译表源，再导入 Godot translation 资源。

### 8.3 本地化落地要求

- UI 文案不要硬编码在脚本逻辑中长期保留。
- 业务状态文本、按钮文案、标签文案、提示文案都应可翻译。
- 模块 README 可以先中文，但面向用户的界面文本必须走本地化系统。

### 8.4 默认要求

- 先保证 `zh_CN`
- 结构上允许后续补 `en`

## 9. 文件交互与桌面行为要求

### 9.1 文件操作必须像桌面工具

- 保存、加载、浏览路径时，应优先弹出系统文件对话框。
- 不应只让用户手填 `user://...` 形式的内部路径。

### 9.2 路径显示要求

- 对用户显示的路径应为系统绝对路径。
- 内部可使用 `user://`、`res://`，但显示层必须做 `globalize_path` 之类的转换。

### 9.3 文件相关 UI 建议模块化

- 凡是出现“文件名/路径/浏览/保存/加载”这一类组合，应优先使用统一模块，而不是每个页面单独重写一套。

## 10. 审查与重构要求

### 10.1 审查不只看对错，也要看复用机会

在审查、重构、补功能时，应额外检查：

- 是否仍有脚本拼 UI 的固定结构
- 是否有可复用组合还散落在页面中
- 是否出现重复文件选择逻辑
- 是否存在可抽象为模块的重复模式
- 是否有脚本知道过多外部节点内部结构
- 是否存在本应经由父节点中介的同级直接耦合
- 是否把 `@export` 用成了叶子节点大杂烩
- 是否存在方法签名、调用方式或模块职责已经变化，但脚本注释和示例仍停留在旧实现

### 10.2 发现可复用元素时的处理原则

- 若影响面小且复用价值明确，应直接抽模块
- 若影响面大但当前正在做相关区域，应同步重构
- 若重构成本高于当前阶段收益，应记录为后续模块化候选

### 10.3 重构交付时应说明

- 哪些结构从代码迁到场景
- 哪些重复逻辑被合并
- 哪些新模块被创建
- 哪些旧脚本职责被缩减

### 10.4 注释同步要求

- 每次修改代码或重构项目时，都必须把注释核验纳入同一批改动，不单独滞后处理。
- 若公开 API、信号语义、参数含义、默认值行为或依赖关系发生变化，必须同步更新：
  - 脚本顶部整体说明
  - 相关方法注释
  - 公开方法调用示例
  - 模块 README 中引用这些 API 的最小示例
- 验收时要同时确认“代码能运行”和“注释描述的是当前真实行为”，两者缺一不可。

## 12. 推荐检查清单

开发或审查前，至少检查以下问题：

### 12.1 场景化检查

- 这个 UI 是否本来就该放进 `.tscn`？
- 当前是否只是把固定节点藏在脚本里生成？
- 页面级场景是否退化成“根节点 + 单一 Card 子节点”？
- 父级滚动和布局是否基于真实子节点最小尺寸，而不是靠硬编码高度顶出来？

### 12.2 模块化检查

- 这段 UI 是否会在别处重复？
- 能否抽成单一职责模块？
- 是否需要独立文件夹与 README？
- 父节点是否只依赖子模块根，而不是依赖子模块内部节点树？
- 模块内部引用是否局限在自身职责范围内？
- 同级协作是否通过 `signal` 与父节点中介完成？
- 当前抽象的是小而稳定的组合控件，还是不可见内容靠脚本注入的大包装模块？

### 12.3 类型检查

- 是否还有未标注类型的关键变量？
- 是否还存在 `:=`？

### 12.4 本地化检查

- 新增用户可见文本是否进入翻译表？
- 是否仍有硬编码文案遗留？

### 12.5 桌面行为检查

- 文件操作是否弹系统对话框？
- 显示给用户的是不是绝对路径？

### 12.6 注释正确性检查

- 每个脚本是否都有整体职责说明和使用方式说明？
- 每个方法前是否都写明了功能和输入参数含义？
- 公开方法是否提供了与当前实现一致的调用示例？
- 本次修改涉及的方法、信号、默认值或依赖关系，是否已经同步更新对应注释？
- 注释中的场景、节点名、参数名、返回值描述是否仍能在当前代码中对应找到？

## 14. 编辑器默认语言显示要求

为了保证场景调试效率，所有用户可见的 UI 节点在 Godot 编辑器中也必须显示默认语言文案，不能只显示翻译 key。

执行要求：

- `.tscn` 中固定可见的 `Label`、`Button`、`RichTextLabel`、`Tab` 标题等，默认文本应填写 `zh_CN` 文案。
- 运行时仍必须通过 `locale/ui_translations.csv` 和统一本地化入口（如 `UICore.translate()`）设置文本，保证多语言扩展。
- 如果控件需要保存翻译 key，应通过脚本导出字段、元数据或绑定函数保存 key，不应牺牲编辑器内的可读性。
- `@tool` UI 模块在编辑器中应尽量调用本地化服务，把默认 key 转换成默认语言显示。
- 审查时必须检查：打开主要场景后，编辑器视图中的按钮、标题、图例和行标签是否能直接读懂，而不是显示 `MAIN_...`、`WORKBENCH_...` 等 key。
